CHAPTER 1 — VISION
================================================================================

1.1 Mission
-----------
Make every device feel like one intelligent system. Users interact with their
entire hardware ecosystem — desktops, servers, Pis, NAS, VMs, containers —
as a single unified platform, controlled by natural language or a polished UI.

1.2 Vision
----------
RenOS becomes the standard open-source control plane for the home and small-
business device mesh. Long-term, it evolves into a full Linux distribution
where RenOS is the operating system itself — not something you install on top.

1.3 Philosophy
--------------
    • AI-first but not AI-dependent. Every action works without AI; AI makes
      it faster and more natural.
    • Local-first by default, cloud optional. Users own their data.
    • Modular to the core. The platform is a kernel of services; everything
      else is a plugin.
    • Secure by default, not as an afterthought.
    • Beautiful inside and out. The API, the CLI, the UI, and the docs all
      meet the same bar.

1.4 Long-Term Goals
-------------------
    1. Connect any device — from a Raspberry Pi Zero to a 128-core server.
    2. Provide a single interface (chat, web, CLI) for the entire device mesh.
    3. Automate everything — updates, backups, deployments, monitoring.
    4. Host a plugin ecosystem with a marketplace.
    5. Evolve into a purpose-built Linux distribution (RenOS Linux) where the
       Core is the init system and the Agent is the device daemon.

1.5 Core Principles
-------------------
    • AI First        — natural language as the primary interaction mode.
    • Local First     — works offline; cloud is additive, not required.
    • Modular         — every feature is a plugin or service; core stays lean.
    • Secure by Default — mTLS, RBAC, audit, encryption, zero trust.
    • Beautiful       — prosumer-grade UI across desktop, tablet, phone.

2.3 Architectural Decisions
---------------------------

    2.3.1 Modular Monolith First
    ----------------------------
    All RenCore services run in a single Go process for v0.1-v1.0. They
    communicate via internal Go interfaces (not HTTP/gRPC loopback). If a
    service needs to scale independently, it is split into its own process
    behind NATS. This avoids distributed systems complexity until profiling
    proves it necessary.

    Trade-off: We sacrifice independent scalability for v1 in exchange for
    simpler deployment, debugging, and development velocity.

    2.3.2 Why Go for Core
    ---------------------
    Go's goroutines, standard library (net/http, crypto/tls), fast compile
    times, and single-binary output make it ideal for a networked control
    plane. Go's static linking keeps the Docker image small.

    2.3.3 Why Rust for Agent
    ------------------------
    The Agent runs on resource-constrained devices (Pi Zero, old laptops)
    and may eventually need direct system calls (cgroups, namespaces,
    eBPF). Rust provides C-level performance with memory safety, no GC
    overhead, and a tiny binary (~5MB stripped).

    2.3.4 Why PostgreSQL + Redis + MinIO + NATS
    -------------------------------------------
    PostgreSQL — relational data with JSONB for flexible metadata. Single
    database for all entities. Well-understood, battle-tested, excellent
    tooling.

    Redis — ephemeral session cache, rate limiter counters, pub/sub for
    real-time UI updates, job queue broker.

    MinIO — S3-compatible blob storage for backups, ISOs, logs, file
    transfers. Self-hosted; no cloud dependency.

    NATS — internal event bus for service decoupling, command dispatch to
    agents, plugin communication. Lightweight, fast, built-in auth.

CHAPTER 3 — COMPONENT RESPONSIBILITIES
================================================================================

3.1 RenCore
-----------
    Purpose: Central orchestration brain. Runs as a Docker container (or
             set of containers when decomposed).

    Responsibilities:
        • Expose REST/gRPC/WebSocket API for RenHub, CLI, and third-party
          clients.
        • Authenticate and authorize every request.
        • Manage device registry (state, metadata, online/offline tracking).
        • Dispatch commands to agents via reliable, queued message bus.
        • Host RenAI and RenFlow engines.
        • Manage plugin lifecycle and sandbox.
        • Store and serve audit logs.
        • Manage file/blob storage.
        • Send notifications to UI and mobile.

    Dependencies: PostgreSQL, Redis, NATS, MinIO, Ollama (optional)

    Failure Handling:
        • Stateless services restart transparently (Kubernetes/Docker
          restart policy).
        • Commands destined for offline agents are queued in NATS with
          TTL. Delivered on reconnect.
        • Database connection loss returns 503; retry with exponential
          backoff.
        • Core crash does NOT affect agents — they continue running,
          cache commands in local SQLite, replay on reconnect.

    Future Expansion:
        • Scale-out: split auth, API, AI, and automation into separate
          processes fronted by a load balancer.
        • Multi-region: federated cores that share device registry.

3.2 RenAgent
------------
    Purpose: Lightweight daemon running on every managed device.

    Responsibilities:
        • Maintain persistent gRPC bidirectional stream to RenCore.
        • Report device health (CPU, RAM, disk, network, uptime, processes)
          at configurable intervals.
        • Execute received commands within a sandbox (cgroup/namespace if
          available, otherwise subprocess with limited privileges).
        • Stream command stdout/stderr back to Core in real-time.
        • Provide reverse tunnel for web services running on the device
          (e.g., access a router admin page via RenOS).
        • Cache commands when offline; replay upon reconnection.
        • Perform self-update (download new binary, verify signature,
          restart).

    Dependencies: None (single binary). Optional: Docker socket if
                  container management is enabled.

    Failure Handling:
        • gRPC disconnection: exponential backoff retry with jitter.
        • Command timeout: kill child process, return error.
        • Disk full: stop caching, alert Core.
        • Agent crash: OS restart policy (systemd/busybox).

    Future Expansion:
        • Act as a mesh node (v2): relay commands to other agents.
        • Embed eBPF probes for kernel-level monitoring.
        • Local AI inference for offline intent parsing.

3.3 RenHub (Web UI)
-------------------
    Purpose: Primary user interface (PWA).

    Responsibilities:
        • Render dashboards, device views, logs, file browser.
        • Provide AI chat interface (RenAI integration).
        • Provide visual workflow editor (RenFlow).
        • Manage settings, users, plugins, permissions.
        • Provide real-time updates via WebSocket.
        • Offline-capable via service worker cache.

    Dependencies: RenCore API.

    Failure Handling:
        • WebSocket disconnect: queue UI actions, reconnect, replay.
        • API failure: show cached data, stale indicator.
        • Complete offline: show cached dashboards, alert user.

    Future Expansion:
        • Native desktop app (Electron/Tauri wrapper).
        • Native mobile apps.

3.4 RenFlow (Automation Engine)
--------------------------------
    Purpose: Trigger-action workflow engine.

    Responsibilities:
        • Manage workflow definitions (DAG of triggers → conditions →
          actions → error handlers).
        • Evaluate triggers (cron, device event, webhook, AI intent).
        • Evaluate conditions (expressions over device state, variables).
        • Execute actions with retry, timeout, and rollback support.
        • Maintain variable store (scoped to workflow, user, global).
        • Schedule recurring workflows.
        • Log every execution step.

    Dependencies: NATS (for event triggers), PostgreSQL (definitions,
                  execution logs), Redis (runtime state).

    Failure Handling:
        • Action failure: configurable retry (count, backoff), then
          escalation (notify, run error handler).
        • Workflow timeout: kill, log partial state.
        • Partial success: mark completed nodes committed; retry from
          failed node (idempotency keys required).

    Future Expansion:
        • Parallel branch execution.
        • Sub-workflow calls (reusable templates).
        • Long-running workflows with human-in-the-loop approval steps.

3.5 RenAI (AI Orchestration)
----------------------------
    Purpose: Bridge between natural language and system actions.

    Responsibilities:
        • Receive natural language input from user.
        • Parse intent using configured AI provider.
        • Map intent to available actions (built-in + plugin-provided).
        • Request user confirmation for destructive operations.
        • Call the action via RenFlow or direct Command Bus.
        • Verify the action result.
        • Report outcome to user in natural language.
        • Maintain conversation context (short-term memory).

    Dependencies: AI provider (Ollama, OpenAI, Anthropic), NATS (action
                  dispatch), PostgreSQL (history).

    Failure Handling:
        • Provider unreachable: fallback to secondary provider, or return
          error "AI backend offline, please try again later."
        • Ambiguous intent: ask clarifying question.
        • Unauthorized action: "You don't have permission to do that."
        • Action fails: "I tried to X but it failed because Y."

    Future Expansion:
        • Multi-step planning (break complex request into sub-actions).
        • Proactive suggestions ("Your disk is 90% full. Clean up old
          backups?")
        • Voice interface.
        • On-device AI agent for offline command parsing.

3.6 Plugin Manager
------------------
    Purpose: Load, sandbox, and manage third-party extensions.

    Responsibilities:
        • Register plugins (Wasm binary or container sidecar).
        • Verify plugin signature.
        • Assign resource limits (CPU, RAM, network).
        • Expose capability-based permission model.
        • Route plugin lifecycle events (install, enable, disable,
          uninstall, update).
        • Serve plugin-defined UI panels to RenHub.
        • Monitor plugin health (heartbeat).

    Dependencies: Wasm runtime (wazero or wasmtime), Container runtime
                  (Docker or Podman), NATS (plugin communication).

    Failure Handling:
        • Plugin crash: restart with backoff, alert admin after N
          consecutive crashes.
        • Plugin OOM: kill, log, disable.
        • Malicious plugin: signature verification failure blocks install.

    Future Expansion:
        • Plugin marketplace with ratings and reviews.
        • Plugin dependency resolution.
        • Plugin sandbox with virtual filesystem.

3.7 Database
------------
    Purpose: Persistent storage for all RenOS state.

    Responsibilities:
        • Store all entity data (users, devices, etc.).
        • Provide migrations (versioned, repeatable).
        • Enforce referential integrity.
        • Support full-text search where needed.

    Dependencies: PostgreSQL.

    Future Expansion:
        • Read replicas for dashboard queries.
        • TimescaleDB extension for time-series metrics.

3.8 API Layer
-------------
    Purpose: Unified ingress for all clients.

    Responsibilities:
        • Terminate TLS.
        • Route to appropriate internal service.
        • Handle rate limiting, request validation, CORS.
        • Upgrade HTTP to WebSocket.
        • Serve gRPC-web for browser clients.

    Dependencies: Reverse proxy (Caddy or Traefik).

    Failure Handling:
        • Rate limit exceeded: 429 with Retry-After header.
        • Backend timeout: 504.
        • Invalid request: 400 with structured error.

3.9 Authentication Service
--------------------------
    Purpose: Identity and access management.

    Responsibilities:
        • Issue and verify JWTs.
        • Manage user accounts, roles, permissions.
        • Handle OAuth2/OIDC flows.
        • Enforce 2FA (TOTP).
        • Issue device certificates (internal CA).
        • Manage API keys for programmatic access.
        • Session management.

    Dependencies: PostgreSQL, Redis (sessions).

    Failure Handling:
        • Auth provider down: cached sessions still valid for N minutes.
        • Token expired: 401, client re-authenticates.
        • Brute force: temporary IP lockout.

3.10 Notification Service
-------------------------
    Purpose: Deliver real-time alerts and events to users.

    Responsibilities:
        • Push WebSocket messages to RenHub.
        • Send push notifications (future native apps).
        • Deliver webhooks to external services.
        • Aggregate and batch notifications.

    Dependencies: Redis (pub/sub), NATS.

4.2 REST API Conventions
-------------------------
    Base URL: https://<renos-host>/api/v1

    • Standard CRUD: GET/POST/PUT/PATCH/DELETE
    • Pagination: ?page=1&per_page=50 (response includes total, next, prev)
    • Filtering: ?field=value (multiple values: ?status=online,offline)
    • Sorting: ?sort=name:asc,created:desc
    • Errors: consistent JSON envelope:
        { "error": { "code": "DEVICE_NOT_FOUND", "message": "...", "details": {} } }
    • Versioning: URL-prefixed (/api/v1). Breaking changes increment version.

4.3 WebSocket Protocol
----------------------
    Endpoint: wss://<renos-host>/api/v1/ws

    Messages are JSON with envelope:
    {
      "type": "event|command|ack",
      "id": "uuid",
      "channel": "devices:status|logs:device-01|notifications",
      "data": { ... },
      "timestamp": "ISO8601"
    }

    Client subscribes to channels; server pushes events.
    Client can send commands (e.g., "subscribe logs:device-01").

4.4 gRPC Agent Protocol
------------------------
    Proto package: renos.agent.v1

    Service AgentService {
        // Bidirectional stream — single connection per agent.
        rpc Connect(stream AgentMessage) returns (stream CoreMessage);

        // One-shot for enrollment (not streaming).
        rpc Enroll(EnrollRequest) returns (EnrollResponse);
    }

    AgentMessage types:
        • HEALTH_REPORT  — CPU, RAM, disk, network, uptime
        • COMMAND_RESULT — stdout, stderr, exit code, duration
        • LOG_LINE       — real-time log output
        • TUNNEL_OPEN    — reverse tunnel request
        • TUNNEL_CLOSE   — tunnel teardown

    CoreMessage types:
        • COMMAND_EXEC   — execute a command
        • COMMAND_CANCEL — kill running command
        • TUNNEL_DATA   — tunnel payload
        • AGENT_UPDATE   — self-update instruction
        • PING           — keepalive

4.5 Event Bus (NATS)
--------------------
    All internal events flow through NATS subjects:

    • renos.device.>             — device events (online, offline, health)
    • renos.command.>            — command dispatch (to agent, to plugin)
    • renos.workflow.>           — RenFlow events (trigger, complete, fail)
    • renos.plugin.>             — plugin lifecycle and communication
    • renos.notification.>       — notifications
    • renos.audit.>              — audit log entries

    Subject hierarchy allows wildcard subscriptions.
    NATS JetStream enabled for durable queuing of commands to offline agents.

4.6 Authentication Flow
-----------------------
    4.6.1 User Login
        RenHub → POST /api/v1/auth/login { username, password, totp? }
        RenCore validates credentials, checks 2FA
        RenCore → RenHub: 200 { access_token, refresh_token, user, expires }

    4.6.2 API Key Usage
        CLI → GET /api/v1/devices (Header: Authorization: Bearer <api_key>)
        RenCore validates API key against RBAC
        RenCore → CLI: 200 [ ... devices ]

    4.6.3 Device Enrollment (detailed in 4.7)

4.7 Device Registration
-----------------------
    Step 1: User generates one-time enrollment token via RenHub
            POST /api/v1/devices/enroll-token
            → { token: "RENOS-ENROLL-XXXX-YYYY", expires: "ISO8601" }

    Step 2: User runs on target device:
            renos enroll --token "RENOS-ENROLL-XXXX-YYYY" --core "https://renos.local:8443"

    Step 3: Agent generates Ed25519 keypair
            Agent sends CSR to RenCore via gRPC Enroll()
            CSR contains: token, device public key, hostname, OS info

    Step 4: RenCore validates token (exists, not expired, not revoked)
            RenCore CA signs device certificate (valid 1 year)
            RenCore stores device fingerprint in database
            RenCore → Agent: signed certificate, CA cert, NATS credentials

    Step 5: Agent stores certificate to disk (encrypted)
            Agent initiates mTLS gRPC stream using new cert
            RenCore marks device "online" in registry

    Step 6: RenHub receives WebSocket event: device.online

CHAPTER 5 — SECURITY
================================================================================

5.1 Security Principles
-----------------------
    1. Zero Trust — no device, user, or service is implicitly trusted.
    2. Least Privilege — every identity gets the minimum access needed.
    3. Defense in Depth — multiple layers: network → TLS → auth → RBAC →
       audit → sandbox.
    4. No Secrets in the Clear — all secrets encrypted at rest and in
       transit.
    5. Immutable Audit — logs are append-only, signed, and cannot be
       modified or deleted by any user.

5.2 Authentication
------------------
    5.2.1 User Authentication
        • Primary: username/password with bcrypt (cost 12)
        • 2FA: TOTP (required for admin role, optional for others)
        • SSO: LDAP / OIDC (Azure AD, Google, GitHub) — optional at deploy
               time
        • Session: JWT access tokens (15m TTL) + refresh tokens (7d TTL,
          rotation)
        • Rate limit: 5 login attempts per IP per minute

    5.2.2 API Key Authentication
        • Scoped keys for automation/CI
        • Key prefixes identify type: renos_sk_ (secret), renos_pk_ (public)
        • Hashed at rest (SHA-256), only prefix shown in UI
        • Revokable individually

    5.2.3 Device Authentication
        • X.509 certificates issued by RenCore's internal CA
        • Ed25519 keypair (small fast keys, high security)
        • Certificate valid 1 year, auto-renewed by agent (30d before
          expiry)
        • Revocation: CRL published by Core; agents check on reconnect

5.3 Authorization (RBAC)
-------------------------
    Built-in roles (hierarchical):

    Role        | Permissions
    ────────────┼────────────────────────────────────────────────────
    admin       | Full access to everything
    operator    | Execute commands, view all devices, view audit logs
    developer   | Deploy apps, manage plugins, manage workflows
    viewer      | Read-only: dashboards, device status, logs
    custom      | User-defined role with granular permission set

    Permissions are structured as:
        <resource>:<action>[:<scope>]

    Examples:
        devices:read:desktop-01
        devices:exec:*
        plugins:install
        workflows:create
        audit:read
        users:manage

    Resources: devices, users, plugins, workflows, audit, settings, secrets

    Actions:   create, read, update, delete, exec, install, manage

5.4 Encryption
--------------
    • In transit: TLS 1.3 minimum. mTLS for agent and service-to-service.
    • At rest: Database encrypted at filesystem level (LUKS or dm-crypt
      recommendation). Application-level encryption for secrets column.
    • Secrets: Encrypted with AES-256-GCM using a master key stored
      in environment variable or Vault. Key derivation per secret.

5.5 Secrets Management
----------------------
    • Option A (default for v1): Master encryption key in environment
      variable. All secrets encrypted in PostgreSQL. RenCore handles
      encryption/decryption in-memory.
    • Option B (recommended for v1.0+): HashiCorp Vault sidecar. RenCore
      requests secret decryption via Vault API.

    Secrets stored: API keys, cloud credentials, SSH keys, database
    passwords for managed services.

5.6 Audit Logging
-----------------
    Every action that changes state is logged:

    • User login/logout (including failures)
    • Command execution (who, what device, what command, result)
    • Device enrollment/deregistration
    • Permission changes
    • Plugin install/remove
    • Workflow create/modify/delete/run
    • Secret access (only that it was accessed, not the secret itself)
    • Settings changes

    Log entry structure:
    {
      "id": "uuid",
      "timestamp": "ISO8601",
      "actor": { "type": "user|device|system|plugin", "id": "..." },
      "action": "devices.exec",
      "target": { "type": "device", "id": "desktop-01" },
      "details": { "command": "sudo apt update", "result": "success" },
      "signature": "base64-ed25519-signature",
      "previous_hash": "sha256-of-previous-entry"
    }

    The chain of hashes forms a hash chain. Tampering with any entry
    breaks all subsequent hashes. Periodic verification job alerts if
    chain is broken.

5.7 Zero Trust Architecture
----------------------------
    • Every request authenticated, regardless of source.
    • No "internal network" bypass.
    • Microservices verify caller identity (JWT for users, cert for agents,
      token for plugins).
    • TLS everywhere: no plaintext internal traffic even in v1 modular
      monolith (loopback TLS is cheap and enforces discipline for when
      services split).

5.8 Recovery Strategy
---------------------
    • Lost admin password: boot RenCore in recovery mode (set env
      RENOS_RECOVERY=true, use one-time recovery URL printed to logs).
    • Compromised device cert: revoke from UI → agent forced to
      re-enroll.
    • Full database loss: restore from encrypted MinIO backups.
      Automated backups run daily with 30-day retention.
    • CA compromise: regenerate CA, re-enroll all devices.

        CREATE TABLE users (

6.3 Migration Strategy
----------------------
    • golang-migrate (or goose) for versioned SQL migrations.
    • Migrations run automatically on RenCore startup.
    • Backward-compatible only: no column drops for 3 versions.
    • Rollback: `migrate down 1` to revert last migration.
    • Schema version tracked in a `schema_migrations` table.

6.4 Data Retention
------------------
    • Audit logs: permanent (immutable by design).
    • Execution logs: 90 days (stdout/stderr blobs: 30 days).
    • Notifications: 30 days.
    • AI conversations: 90 days (user-configurable).
    • Sessions: deleted on expiry (cleanup job runs hourly).
    • Soft-deleted users: purged after 30 days.

7.2 Plugin Lifecycle
--------------------
    ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌──────────┐
    │         │   │         │   │         │   │          │   │          │
    │ Pending │──►│Verified │──►│ Active  │──►│Disabled  │──►│Uninstalled│
    │         │   │         │   │         │   │          │   │          │
    └─────────┘   └─────────┘   └─────────┘   └──────────┘   └──────────┘
        │              │             │              │
        │ (sig fail)   │             │              │
        ▼              ▼             ▼              ▼
    ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌──────────┐
    │Rejected │   │ Blocked │   │ Error   │   │  (data   │
    │         │   │         │   │         │   │  purged) │
    └─────────┘   └─────────┘   └─────────┘   └──────────┘

    States:
    • Pending: uploaded, not yet verified.
    • Verified: signature checks pass.
    • Active: running and accepting requests.
    • Disabled: stopped but not uninstalled.
    • Error: crashed repeatedly, auto-disabled.
    • Blocked: signature invalid or permission escalation detected.
    • Uninstalled: removed from database; data cleaned up.

7.3 Plugin Manifest
-------------------
    Every plugin includes a manifest (plugin.yaml or embedded in Wasm):

    ```yaml
    name: minecraft-manager
    version: 1.0.0
    type: container          # wasm | container
    description: Manage Minecraft servers
    author: RenOS Community
    icon: https://...

    permissions:
      - devices:exec:mc-*    # can execute on devices matching label mc-*
      - secrets:read:mc-*    # can read secrets prefixed mc-
      - notifications:write  # can send notifications

    container:
      image: ghcr.io/renos-plugins/minecraft-manager:1.0.0
      ports:                 # optional ports to expose
        - internal: 25565
          protocol: tcp
      volumes:
        - path: /data
          size: 10Gi

    wasm:
      entrypoint: plugin.wasm
      max_memory: 64MB
      exports:
        - handle_event
        - handle_command
        - render_panel

    config_schema:           # JSON Schema for user-configurable settings
      type: object
      properties:
        max_players:
          type: integer
          default: 20
        motd:
          type: string

    lifecycle:
      on_install: []         # hooks executed at each lifecycle stage
      on_uninstall: []
      on_update: []
    ```

7.4 Plugin Communication
-------------------------
    All plugins communicate with RenCore via NATS, regardless of type.

    Wasm plugins: Plugin Manager invokes exported functions. If the plugin
    needs to call Core APIs, the Plugin Manager proxies requests over NATS
    on the plugin's behalf.

    Container plugins: The container connects to NATS directly using
    credentials injected at startup.

    Subject convention:
        renos.plugin.<plugin_id>.request
        renos.plugin.<plugin_id>.response
        renos.plugin.<plugin_id>.event

    Plugin API (gRPC over NATS):
        • CallDeviceAction(device_id, action, params) → Result
        • ReadSecret(name, scope) → Secret (audit logged)
        • SendNotification(user_id, title, body) → void
        • RegisterTrigger(trigger_def) → trigger_id
        • EmitEvent(event_type, data) → void
        • GetDeviceStatus(device_id) → DeviceStatus
        • WriteAuditLog(action, details) → void

7.5 Plugin Permissions
-----------------------
    Permissions are declared in the manifest. At install time, the user
    reviews and must approve them. Permissions can be narrowed after
    install.

    Permission enforcement:
    1. Plugin Manager checks every API call against declared permissions.
    2. Any violation is logged to audit and blocks the call.
    3. Repeated violations auto-disable the plugin.

7.6 Plugin Updates
-------------------
    • New manifest uploaded; version must be higher than current.
    • Permissions diff presented to user for approval.
    • On approval: Wasm binary replaced and runtime restarted, or container
      image pulled and container recreated.
    • Database migrations owned by plugin (if any) run automatically.

7.7 Plugin Marketplace (Future)
-------------------------------
    • Central registry at marketplace.renos.io
    • Plugins published as signed OCI artifacts.
    • RenCore can browse, install from marketplace with one command.
    • Rating and review system.
    • Automated security scanning of submitted plugins.

CHAPTER 8 — AUTOMATION ENGINE (RenFlow)
================================================================================

8.1 Design Philosophy
---------------------
    RenFlow treats automation as a directed acyclic graph (DAG) of nodes.
    Each node is a step: trigger, condition, action, or control flow.
    This scales from "if this then that" to multi-branch enterprise
    workflows.

8.2 Workflow Structure
-----------------------
    {
      "id": "uuid",
      "name": "Backup NAS to Cloud",
      "description": "Weekly encrypted backup",
      "triggers": [
        { "type": "cron", "config": { "expression": "0 3 * * 0" } },
        { "type": "manual", "config": {} }
      ],
      "nodes": [
        {
          "id": "check-disk",
          "type": "condition",
          "config": {
            "expression": "device('nas-01').disk_usage_percent < 90"
          },
          "next_on_true": "run-backup",
          "next_on_false": "send-alert"
        },
        {
          "id": "run-backup",
          "type": "action",
          "config": {
            "action_type": "command",
            "device": "nas-01",
            "command": "restic backup /data --tag weekly",
            "timeout": 3600
          },
          "retry": { "count": 2, "backoff": "exponential" },
          "next_on_success": "verify-backup",
          "next_on_failure": "send-alert"
        },
        {
          "id": "verify-backup",
          "type": "action",
          "config": {
            "action_type": "command",
            "device": "nas-01",
            "command": "restic check",
            "timeout": 300
          },
          "next_on_success": "notify-success",
          "next_on_failure": "send-alert"
        },
        {
          "id": "send-alert",
          "type": "action",
          "config": {
            "action_type": "notify",
            "title": "Backup failed",
            "body": "NAS backup workflow failed at step {{ node.name }}",
            "severity": "error"
          }
        },
        {
          "id": "notify-success",
          "type": "action",
          "config": {
            "action_type": "notify",
            "title": "Backup complete",
            "body": "Weekly backup completed successfully.",
            "severity": "success"
          }
        }
      ],
      "variables": {
        "backup_date": { "type": "string", "value": "{{ now() | date '2006-01-02' }}" }
      },
      "error_handler": {
        "type": "notify",
        "config": { "severity": "critical", "title": "Workflow crashed" }
      }
    }

8.3 Trigger Types
-----------------
    +----------+----------------------------------------------------------+
    | Type     | Description                                              |
    +----------+----------------------------------------------------------+
    | cron     | Schedule: cron expression + timezone                     |
    | event    | Device or system event: device.online, device.disk_full  |
    | webhook  | External HTTP POST to a unique URL                       |
    | manual   | User clicks "Run" in UI                                  |
    | ai       | User says a phrase matching a pattern via RenAI          |
    | schedule | One-shot at a future datetime                            |
    +----------+----------------------------------------------------------+

8.4 Condition Expressions
-------------------------
    Expressions use a simple DSL (evaluated safely — no eval()):

    • device("<id>").<metric> <operator> <value>
        device("desktop-01").cpu_percent > 80
        device("server-01").memory_available_gb < 4

    • env("<name>") <operator> <value>
        env("backup_target") == "s3"

    • {{ variable }} <operator> <value>
        {{ backup_date }} != ""

    • last_run("<workflow_id>").<field>
        last_run("backup-workflow").status == "success"

    Operators: ==, !=, >, <, >=, <=, contains, matches (regex),
               in (list), between (range)

    Compound: and, or, not, parentheses

8.5 Action Types
-----------------
    +-----------+--------------------------------------------------------+
    | Type      | Description                                              |
    +-----------+--------------------------------------------------------+
    | command   | Execute command on device (with timeout, env vars)       |
    | notify    | Send notification to user(s)                             |
    | api       | Make HTTP request to external service                    |
    | workflow  | Call another workflow (sub-workflow with data passing)   |
    | plugin    | Call a plugin action                                     |
    | wait      | Pause for duration or until condition is met             |
    | condition | Branch based on expression (if/else)                     |
    | loop      | Iterate over list (for-each with variable binding)       |
    | set       | Set a variable value                                     |
    | script    | Execute a short script (Lua embedded in RenCore)         |
    +-----------+--------------------------------------------------------+

8.6 Execution Engine
---------------------
    • Workflow runner picks up triggered workflows from NATS queue.
    • Each node execution is tracked in PostgreSQL (exec_logs).
    • Runner supports:
        - Parallel node execution (fan-out)
        - Sequential execution
        - Conditional branching
        - Retry with configurable backoff
        - Timeout cancellation
        - Idempotency (re-running a failed workflow doesn't duplicate
          side effects if actions declare idempotency keys)
    • Workflow execution is async — user gets real-time updates via
      WebSocket.

8.7 Variable System
-------------------
    Variables can be:
    • Workflow-scoped: exist only during execution.
    • User-scoped: persist across workflows for a user.
    • Global: available to all workflows.

    Variable interpolation: {{ variable_name }}, with pipe filters:
    {{ date | format "2006-01-02" }}, {{ string | upper }}

    Filter library: date, upper, lower, trim, split, join, default, json

8.8 Error Handling
------------------
    Per-node:
    • retry.count — how many times to retry
    • retry.backoff — linear | exponential | fixed
    • next_on_failure — node to jump to on persistent failure

    Workflow-level:
    • error_handler — node that runs if any unhandled error occurs

    Errors are logged to audit and visible in workflow execution history.

CHAPTER 9 — AI ARCHITECTURE (RenAI)
================================================================================

9.1 Design Principle
--------------------
    RenAI does NOT control systems directly. It is an orchestration layer
    that converts natural language into safe, permission-checked,
    auditable actions. The AI is a translator and planner, never an
    executor.

    Flow: User Request → Intent → Plan → Permission Check → Execute →
          Verify → Report

9.2 Architecture
----------------

    ┌──────────┐     ┌─────────────────────────────────────────────────┐
    │  User    │     │                  RenAI                          │

                     │  │(Ollama/ │  │ Parser  │  │    Gate       │  │
                     │  │ OpenAI/ │  │ (NLU →  │  │ (Check RBAC)  │  │

9.3 Provider Abstraction
-------------------------
    RenAI defines a uniform interface for all AI providers:

    interface AIProvider {
        Chat(messages, tools, options) → Response
        StreamChat(messages, tools, options) → Stream<Response>
        Embed(text) → Vector (future)
    }

    Implementations:
    • OllamaProvider — local, works offline, supports any model
    • OpenAIProvider — GPT-4o, GPT-4, GPT-3.5
    • AnthropicProvider — Claude 3 Opus/Sonnet/Haiku
    • GenericOpenAIProvider — any OpenAI-compatible API (vLLM, TGI, etc.)

    Configuration:
    ```yaml
    ai:
      default_provider: ollama
      providers:
        ollama:
          type: ollama
          model: llama3.1:70b
          base_url: http://ollama:11434
        openai:
          type: openai
          api_key: "${RENOS_OPENAI_KEY}"
          model: gpt-4o
        anthropic:
          type: anthropic
          api_key: "${RENOS_ANTHROPIC_KEY}"
          model: claude-3-opus-20240229
    ```

9.4 Intent Parsing
------------------
    User input is sent to the AI provider with a system prompt that
    defines available tools (actions). The AI returns structured tool
    calls.

    System prompt includes:
    • Available devices (name, OS, status)
    • Available actions (tool definitions in OpenAI format)
    • Permissions context (what the user can do)
    • Constraints (never run destructive commands without confirmation)

    Tool definition example (OpenAI format):
    ```json
    {
      "type": "function",
      "function": {
        "name": "execute_command",
        "description": "Run a shell command on a device",
        "parameters": {
          "type": "object",
          "properties": {
            "device": { "type": "string", "description": "Device hostname or ID" },
            "command": { "type": "string", "description": "Command to execute" },
            "timeout": { "type": "integer", "description": "Timeout in seconds" }
          },
          "required": ["device", "command"]
        }
      }
    }
    ```

9.5 Permission Gate
-------------------
    Before any tool call is executed, RenAI checks:
    1. Does the user's role have permission for this action on this target?
    2. If yes, execute.
    3. If no, return error to user: "You don't have permission to do that."

    Destructive actions (reboot, delete, format, shutdown, install):
    • Always require explicit user confirmation unless overridden by
      setting.
    • RenAI returns: "I can reboot desktop-01. Shall I proceed?"

9.6 Multi-Step Planning (Future)
---------------------------------
    For complex requests ("Set up a Minecraft server with 4GB RAM, back it
    up daily, and alert me if CPU exceeds 80%"), RenAI will:

    1. Parse the intent
    2. Break into sub-actions (install server, configure RAM, create backup
       workflow, create alert workflow)
    3. Present the plan to the user for approval
    4. Execute each step sequentially
    5. Report overall success/failure

9.7 Skills (Extensible Capabilities)
-------------------------------------
    Skills are packages that extend RenAI's knowledge. A skill defines:

    • New tool definitions (what the AI can do)
    • Example prompts (few-shot learning examples)
    • Validation rules

    Skills can be:
    • Built-in (core RenOS capabilities)
    • Plugin-provided (a monitoring plugin adds "check_health" skill)
    • User-defined (custom prompts and tools)

    Skills will be loaded into the system prompt dynamically.

9.8 Offline Behavior
--------------------
    When no AI provider is reachable (no local Ollama, no cloud):
    • RenAI returns a clear message: "AI backend is not available.
      Please check your AI provider configuration."
    • The rest of RenOS continues working normally.
    • Users can still use UI and CLI directly.

    • Minor versions every 4-6 weeks.
    • Major versions every 6-12 months.
    • LTS releases every 2 years (starting at v1.0).

-----------------

    v0.1 — "Foundation" (Months 1-3)
    ─────────────────────────────────

        • RenAgent single binary (Linux amd64 + arm64)
        • mTLS device enrollment flow
        • Basic web UI: device list, status, health metrics

        • RenHub: AI chat interface, per-device dashboards, log viewer
        • Agent auto-update mechanism
        • CLI tool (renos status, renos exec, renos logs, renos enroll)
        • Audit log hash chain verification
        • macOS and Windows agent support

    v0.3 — "Automation" (Months 7-9)

        • RenFlow engine: cron/webhook/event triggers, conditions,

        • Notification system with WebSocket push
        • Workflow templates (pre-built: backup, update, health check)
