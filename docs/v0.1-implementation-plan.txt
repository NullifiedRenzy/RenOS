M04 — POSTGRESQL SCHEMA + MIGRATIONS
================================================================================

GOAL
  All v0.1 tables created via automated migrations. The schema covers
  the entities needed for enrollment and heartbeat: users, devices,
  sessions, audits, settings.

FILES / FOLDERS
  core/migrations/
  ├── 000001_create_users.up.sql
  ├── 000001_create_users.down.sql
  ├── 000002_create_devices.up.sql
  ├── 000002_create_devices.down.sql
  ├── 000003_create_sessions.up.sql
  ├── 000003_create_sessions.down.sql
  ├── 000004_create_audits.up.sql
  ├── 000004_create_audits.down.sql
  └── 000005_create_settings.up.sql
  └── 000005_create_settings.down.sql

  core/internal/
  └── db/
      └── migrate.go            # golang-migrate runner (embedded SQL)

ACCEPTANCE CRITERIA
  - `go run ./cmd/renos-core migrate` runs all up migrations
  - All tables exist in PostgreSQL
  - Running again is idempotent (no errors)
  - `migrate down 1` rolls back last migration
  - Foreign keys, unique constraints, and check constraints are enforced
  - INSERT/UPDATE/DELETE works against all tables
  - Down migrations restore previous state

TABLES (v0.1 subset from architecture spec)
  users
    id UUID PK, email UNIQUE, password TEXT, display_name TEXT,
    role TEXT DEFAULT 'viewer', totp_secret TEXT nullable,
    totp_enabled BOOLEAN DEFAULT FALSE, settings JSONB DEFAULT '{}',
    created_at, updated_at, deleted_at TIMESTAMPTZ nullable

  devices
    id UUID PK, user_id UUID FK→users, hostname TEXT, os TEXT,
    arch TEXT, agent_version TEXT, cert_fingerprint TEXT UNIQUE,
    enrolled_at TIMESTAMPTZ, last_seen TIMESTAMPTZ,
    status TEXT DEFAULT 'offline',
    labels JSONB DEFAULT '{}', capabilities JSONB DEFAULT '[]',
    metadata JSONB DEFAULT '{}', created_at, updated_at

  sessions
    id UUID PK, user_id UUID FK→users, token_hash TEXT UNIQUE,
    device_info TEXT, ip_address INET, expires_at TIMESTAMPTZ,
    created_at

  audits
    id UUID PK, timestamp TIMESTAMPTZ, actor_type TEXT, actor_id TEXT,
    action TEXT, target_type TEXT, target_id TEXT,
    details JSONB DEFAULT '{}', signature TEXT, prev_hash TEXT,
    created_at

  settings
    key TEXT PK, value JSONB, scope TEXT DEFAULT 'global', updated_at

RISKS
  - Migration ordering with foreign keys → migrations must run in order;
    use version numbers, not timestamps, for ordering
  - Down migration drops column used by later migration → never drop
    columns until they've had 2+ versions of deprecation window
  - Embedded SQL files require Go embed → use //go:embed

COMMANDS
  psql -h localhost -U renos -d renos -f migrations/000001_create_users.up.sql
  go run ./cmd/renos-core migrate
  psql -h localhost -U renos -d renos -c "\dt"
  go run ./cmd/renos-core migrate down 1

M06 — DEVICE ENROLLMENT (CORE + AGENT)
================================================================================

GOAL
  End-to-end enrollment flow: admin generates token from Core's API,
  agent presents token → receives signed certificate → establishes mTLS
  gRPC connection. Device is registered in the database.

FILES / FOLDERS
  core/internal/
  ├── api/
  │   └── devices.go            # POST /devices/enroll-token, handlers
  ├── auth/
  │   ├── jwt.go                # JWT issue + verify (used for user auth)
  │   ├── totp.go               # TOTP verify (placeholder)
  │   └── password.go           # bcrypt hash + verify
  ├── agent/
  │   ├── manager.go            # Agent connection tracker (map of conns)
  │   ├── grpc_server.go        # gRPC server: Enroll + Connect handlers
  │   └── enroll.go             # Token validation + cert signing
  ├── ca/
  │   ├── ca.go                 # Internal CA: generate key, sign CSR
  │   └── cert.go               # X.509 cert creation helpers
  ├── api/
  │   └── router.go             # Mount device routes + gRPC on same port
  ├── db/
  │   ├── users.go              # User repository (create, find by email)
  │   └── devices.go            # Device repository (create, find, update)
  └── config/
      └── config.go             # Added RENOS_EXTERNAL_URL, CA fields

  core/cmd/renos-core/
  └── main.go                   # Wire CA, gRPC server, agent manager

  agent/src/
  ├── enroll.rs                 # Enroll flow: CSR gen → send → store cert
  ├── grpc_client.rs            # Add mTLS with device cert
  └── identity.rs               # Expanded: keypair gen, cert storage

  proto/agent/v1/
  └── agent.proto               # Fleshed out EnrollRequest/Response

ACCEPTANCE CRITERIA
  - POST /api/v1/devices/enroll-token (with admin JWT) → 201 { token,
    expires }
  - `renos-agent enroll --token X --core https://localhost:8443` exits 0
  - Device row created in `devices` table with correct hostname, OS,
    arch, cert fingerprint
  - Certificate stored at /var/lib/renos/identity.pem (Linux)
  - Agent starts in normal mode, loads cert, establishes mTLS gRPC
    connection to Core
  - Core marks device "online" in database
  - Audit entry created for enrollment event
  - Re-enrollment with expired token → rejected
  - Enrollment from unauthenticated request → 401

RISKS
  - gRPC + HTTP on same port → use cmux or separate ports (v1: separate
    ports; document in config)
  - CA key management in dev → auto-generate on first boot, store in
    DB encrypted
  - mTLS cert verification → test with expired cert, wrong CA, revoked
    cert
  - Windows agent enrollment → skip for v0.1 (Linux + macOS only)

COMMANDS
  # Core startup
  cd core && go run ./cmd/renos-core

  # Generate enrollment token
  TOKEN=$(curl -s -X POST http://localhost:8443/api/v1/devices/enroll-token \
    -H "Authorization: Bearer $(admin_jwt)" | jq -r '.token')

  # Enroll agent
  cd agent && cargo run -- enroll --token "$TOKEN" --core http://localhost:8443

  # Start agent normally
  cd agent && cargo run --

  # Verify
  curl -s http://localhost:8443/api/v1/devices \
    -H "Authorization: Bearer $(admin_jwt)" | jq '.'
  # → device should show "online"

M07 — HEARTBEAT REPORTING
================================================================================

GOAL
  Agent sends periodic health reports on the gRPC stream. Core receives
  them, updates the device's `last_seen` and `status` fields, and makes
  health data available via REST API.

FILES / FOLDERS
  core/internal/
  ├── agent/
  │   ├── manager.go            # Handle incoming HealthReport messages
  │   └── stream.go             # Bidirectional stream handler per agent
  ├── db/
  │   └── devices.go            # Update last_seen, status, metadata
  └── api/
      └── devices.go            # GET /devices/:id returns health metrics

  agent/src/
  ├── health.rs                 # Collect system info (CPU, RAM, disk)
  ├── executor.rs               # Placeholder command executor
  └── grpc_client.rs            # Send HealthReport every 30s

  proto/agent/v1/
  └── agent.proto               # Add HealthReport message definition

ACCEPTANCE CRITERIA
  - Agent sends HealthReport every 30s (±5s jitter)
  - Core updates devices.last_seen on each report
  - GET /api/v1/devices/:id returns CPU, RAM, disk, uptime
  - If Core doesn't receive heartbeat for 90s, device marked "offline"
  - Offline device returns to "online" on next heartbeat
  - Health metrics stored in devices.metadata JSONB (for v0.1; time-
    series storage deferred to v0.2)
  - Agent CPU usage while idle: < 1% (measured)
  - Agent RAM usage: < 20MB (measured)

RISKS
  - sysinfo crate may not report all metrics on macOS → tier 2 for v0.1;
    document limitations
  - Heartbeat data volume at scale → for v0.1 it's metadata JSONB, no
    concern
  - Time sync issues → all timestamps in UTC, set on Core side

COMMANDS
  # Start Core
  cd core && go run ./cmd/renos-core

  # Start Agent (after enrollment)
  cd agent && cargo run --

  # Wait 30s, then check
  curl -s http://localhost:8443/api/v1/devices --header "Authorization: Bearer $(admin_jwt)" | jq '.data[0].last_seen, .data[0].status'

  # Check agent logs for health report
  # Check Core logs for incoming health reports

M09 — WEBSOCKET LIVE UPDATES
================================================================================

GOAL
  Real-time updates flow from Agent → Core → Browser via WebSocket.
  Dashboard and device page update without page refresh.

FILES / FOLDERS
  core/internal/
  ├── api/
  │   ├── ws.go                  # WebSocket upgrade handler
  │   └── ws_hub.go             # Connection hub (register/unregister/broadcast)
  ├── api/
  │   └── router.go             # Add WS endpoint: /api/v1/ws
  └── agent/
      └── manager.go            # Publish agent events to NATS

  hub/
  ├── lib/
  │   └── ws-client.ts          # WebSocket client with reconnect
  ├── hooks/
  │   ├── use-websocket.ts      # Subscribe to channels, dispatch events
  │   └── use-devices.ts        # Invalidate queries on WS event
  ├── components/
  │   ├── devices/
  │   │   └── device-status-dot.tsx  # Pulse animation for online
  │   └── dashboard/
  │       └── recent-activity.tsx    # Live activity feed
  └── stores/
      └── ui-store.ts           # Add lastEvent for cross-component state

EVENT TYPES (v0.1 subset)
  device.online     → device card shows green dot
  device.offline    → device card shows gray dot
  device.health     → health bars update in place (no flash)
  command.started   → activity feed: "desktop-01: running apt update"
  command.completed → activity feed: "desktop-01: apt update completed"

ACCEPTANCE CRITERIA
  - WebSocket connection established on login
  - Device online/offline events update UI without refresh
  - Health updates (CPU%) reflect on dashboard within 5s of agent
    sending heartbeat
  - Reconnection: WS drops → client reconnects with backoff → state
    resyncs
  - 50+ simultaneous WebSocket connections maintain < 1% CPU increase
  - Events stop arriving after user logs out

RISKS
  - WebSocket behind reverse proxy (Caddy/Traefik) → ensure proxy
    supports WS; document in deploy guide
  - Connection state management in React → use Zustand for UI state,
    WebSocket for events; avoid coupling
  - Reconnection storm if Core restarts → jitter on client reconnect

COMMANDS
  # Core + agent running, agent sending heartbeats
  # Open two browser tabs: dashboard + device page
  # Kill agent → device should show offline within 90s
  # Restart agent → device should show online within 30s
