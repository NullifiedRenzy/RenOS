Getting Started with RenOS

RenOS is an open-source, self-hosted device management platform designed to manage desktops, servers, VMs, Docker containers, NAS, and mobile devices from a single unified interface. It provides secure remote command execution, real-time monitoring, automation, and AI-powered operations.

Overview

RenOS is built on a modular architecture with four primary components: a Go-based Core server that handles API and orchestration, a Rust-based Agent that runs on managed devices, a Next.js-based Hub for the web UI, and a Protobuf-based communication layer. The platform uses PostgreSQL for persistence, Redis for caching and pub/sub, and NATS for messaging between services.

🚀 Core

Go backend service handling REST API, WebSocket connections, job scheduling, authentication, and device orchestration.

🤖 Agent

Rust-based lightweight agent deployed on managed devices. Supports Linux, macOS, Windows, and ARM architectures.

💻 Hub

Next.js + React + TypeScript web interface for managing devices, viewing dashboards, and configuring automation.

📡 Messaging

NATS provides real-time message delivery between Core and Agents. Redis handles caching and pub/sub for events.

Quick Start Guide

Get RenOS running in under 5 minutes with Docker:

1

Clone the repository: git clone https://github.com/renos-project/renos.git && cd renos

2

Run the installer: ./install.sh — this starts PostgreSQL, Redis, NATS, and the Core server.

3

Access the Hub at http://localhost:8443 and log in with admin@renos.local / admin.

4

Install the Agent on a device: curl -fsSL https://your-server/install.sh | bash

5

Start managing your devices from the dashboard or CLI.

Architecture Overview

RenOS follows a hub-and-spoke architecture. The Core server acts as the central hub, managing communication with all connected agents. Agents establish outbound WebSocket or mTLS connections to the Core, enabling management even behind NAT or firewalls.

+----------------+ +----------------+ | Hub (Web) | | renctl (CLI) | | Next.js/React | | Go binary | +-------+--------+ +-------+--------+ | | | HTTP/WebSocket | v v +--------------------------------------------------+ | Core Server (Go) | | +----------+ +-----------+ +---------------+ | | | REST API | | Scheduler | | Job Processor | | | +----------+ +-----------+ +---------------+ | | +----------+ +-----------+ +---------------+ | | | Auth | | Plugin | | AI Engine | | | +----------+ +-----------+ +---------------+ | +-----+------------+------------+------------------+ | | | gRPC/mTLS PostgreSQL Redis/NATS | | | +-----v------------v------------v------------------+ | Agent (Rust) | | +----------+ +-----------+ +---------------+ | | | Executor | | Heartbeat | | Update Mgr | | | +----------+ +-----------+ +---------------+ | | +----------+ +-----------+ | | | Docker | | Systemd | | | +----------+ +-----------+ | +--------------------------------------------------+

Security Model

RenOS implements a defense-in-depth approach: all agent communication uses mutual TLS (mTLS) or WebSocket with JWT authentication. The platform enforces role-based access control (RBAC) on every API endpoint, encrypts secrets at rest using AES-256-GCM, and logs all administrative actions for audit purposes. Rate limiting, CSRF protection, and Content Security Policy headers protect the web interface.

Architecture

High-Level Architecture

RenOS is organized as a monorepo containing four main components: Core (Go), Agent (Rust), Hub (Next.js/TypeScript), and Proto (shared Protobuf definitions). This approach is formalized in ADR-001, which was accepted after considering multi-repo alternatives. The monorepo ensures that cross-component changes land in a single commit and that CI runs all tests together.

Repository Structure: renos/ core/ # Go backend agent/ # Rust agent hub/ # Next.js frontend proto/ # Shared protobuf deploy/ # Docker, nginx configs scripts/ # Dev & ops scripts docs/ # Documentation

Component Architecture

Core (Go)

The Core server is written in Go, chosen for its excellent standard library for HTTP/gRPC servers, lightweight goroutine concurrency model for managing many agent connections, fast compile times, and single-binary deployment. Core handles:

  • REST API — All management endpoints under /api/v1/
  • WebSocket Hub — Real-time device communication and event streaming
  • Job Scheduler — Cron-based and triggered job execution
  • Authentication — JWT issuance, OAuth2, SSO providers
  • Plugin System — Plugin loading, lifecycle, and API gateway
  • AI Engine — Provider-agnostic AI integration layer

Agent (Rust)

The device agent is written in Rust for C-level performance with memory safety and no garbage collector. It compiles to a tiny ~5MB static binary suitable for Raspberry Pi Zero, with excellent cross-compilation support for ARM/aarch64.

  • Command Executor — Run shell commands with policy enforcement
  • Heartbeat — Periodic health and status reporting
  • Docker Manager — Container, image, volume, network operations
  • Systemd Manager — Service status and control
  • File System — File browsing, upload/download, permissions
  • Update Manager — Self-update and OS package management

Hub (Next.js + React + TypeScript)

The web UI uses Next.js with React and TypeScript. Server components provide fast initial loads, and the App Router delivers layouts, loading states, and error boundaries. The Hub communicates with Core via REST API and WebSocket for real-time updates.

Data Flow

User Action --> Hub (HTTP) --> Core API --> Database | NATS Pub/Sub | Agent(s) (WebSocket/mTLS) | Execute Command | Result --> NATS --> Core --> Hub --> User

When a user initiates a command through the Hub or CLI, the request flows through the Core API, which publishes the command to NATS. The target agent receives the command via its persistent connection, executes it within the configured security policies, and publishes the result back through NATS to the Core, which stores it and notifies the Hub via WebSocket.

Security Architecture

Security is enforced at every layer: JWT tokens authenticate API requests, RBAC authorizes actions, mTLS secures agent connections, input validation prevents injection attacks, and CSP blocks XSS. Secrets are encrypted with AES-256-GCM at rest, and all administrative actions are audit-logged.

go build -o renos-core .

cargo build --release

npm install

# Start Core (requires PostgreSQL, Redis, NATS running)
./renos-core --config config.yaml

Agents

Agent Overview

The RenOS Agent is a lightweight Rust binary that runs on managed devices. It establishes a persistent secure connection to the Core server and executes commands, reports telemetry, manages containers, and more. The agent is designed to be minimal (~5MB binary), secure (no open ports required), and resilient (automatic reconnection with exponential backoff).

The agent can be configured via command-line flags, environment variables, or a YAML config file at /etc/renos/agent.yaml:

yaml

tls_skip_verify: false
heartbeat_interval: 60

  - production
  - webserver

  - command_exec
  - docker
  - systemd
  - file_system

  allowed_commands:
    - "systemctl *"
    - "docker *"
    - "df -h"
  blocked_commands:
    - "rm -rf /*"
    - "mkfs*"

Heartbeats

Agents send heartbeats to the Core at a configurable interval (default: 60 seconds). Each heartbeat contains system metrics (CPU, memory, disk, network), running processes and services, agent version and uptime, Docker container status, and pending command acknowledgments. Heartbeats are visible in the Hub dashboard and accessible via the API at GET /api/v1/devices/{id}/heartbeats.

Agent Updates

Agents can self-update automatically. The Core distributes new agent binaries, and the agent performs a safe rolling update:

bash
# Trigger update from CLI
renctl agent update --target all

# Or target specific devices
renctl agent update --target device-uuid-1,device-uuid-2

# Check agent versions
renctl agent list --show-version

Plugins

Plugin Architecture

RenOS supports a plugin system that extends Core, Agent, and Hub capabilities. Plugins are self-contained packages that can add new API endpoints, device actions, UI components, or automation triggers. The plugin system uses WebAssembly (WASM) for Core plugins and native modules for Agent plugins, providing sandboxed execution with well-defined APIs.

Creating Plugins

Plugins can be written in any language that compiles to WebAssembly (Go, Rust, AssemblyScript, etc.) or as native modules in Go (for Core) or Rust (for Agent).

Minimal Core Plugin (Go)

go
package main

import "renos/plugin"

func init() {
    plugin.Register(&MyPlugin{})
}

type MyPlugin struct{}

func (p *MyPlugin) Name() string { return "my-plugin" }
func (p *MyPlugin) Version() string { return "1.0.0" }

func (p *MyPlugin) Init(ctx plugin.Context) error {
    ctx.Router().Get("/hello", func(c plugin.Context) error {
        return c.JSON(200, map[string]string{"message": "Hello from plugin!"})
    })
    return nil
}

func (p *MyPlugin) Close() error { return nil }

Agent Plugin (Rust)

rust
use renos_agent_sdk::{Capability, Context};

struct HealthCheck;

impl Capability for HealthCheck {
    fn name(&self) -> &str { "health-check" }
    fn version(&self) -> &str { "1.0.0" }

    fn execute(&self, ctx: &Context, args: &[String]) -> Result<String, String> {
        let output = std::process::Command::new("uptime").output().unwrap();
        Ok(String::from_utf8_lossy(&output.stdout).to_string())
    }
}

renos_agent_sdk::export!(HealthCheck);

Plugin API

The plugin API provides access to: HTTP Router (register custom API endpoints), Database (read/write access to plugin-scoped tables), Event Bus (subscribe to and publish internal events), Logger (structured logging with the platform logger), Secrets (access encrypted secrets vault), and Device API (execute commands and read device state).

Marketplace

Plugins are distributed through the RenOS Marketplace. Users can browse, install, and manage plugins directly from the Hub UI or CLI. Publishing requires package signing with a developer key and passing automated compatibility and security validation.

AI Integration

RenAI Overview

RenAI is RenOS's built-in AI engine that provides natural-language device management, intelligent alert correlation, automated troubleshooting, and predictive maintenance. It supports both local and cloud AI models through a provider-agnostic architecture.

💡 Anthropic

Prompt Engineering

RenAI uses carefully crafted system prompts that define the AI's role as a device management assistant. Prompts include system context (available devices, their capabilities, and current state), safety constraints (prohibited operations), output format (structured JSON for machine parsing, Markdown for human display), and tool definitions (available API functions the AI can invoke).

text
You are RenAI, a device management assistant for RenOS.
Available devices:
- webserver-01 (Linux, online, Docker running)
- database-02 (Linux, online, Postgres active)
- office-mac (macOS, online)

Available actions:
- run_command(device, command)
- get_logs(device, filter)
- list_containers(device)
- restart_service(device, service)

Safety rules:
- Never run destructive commands (rm -rf, mkfs, dd)
- Confirm before restarting critical services
- Flag suspicious patterns to the user

Context Building

RenAI automatically builds context for each interaction by gathering device inventory and status from the database, recent events and alerts from the event log, current system metrics (CPU, memory, disk), user's role and permissions, and conversation history (last 20 turns). This context is injected into the prompt before each AI call, ensuring the model has up-to-date information about the managed environment.

Automation

Workflows

RenOS provides a powerful automation engine for creating multi-step workflows. Workflows consist of triggers, conditions, and actions that execute in sequence or parallel across one or many devices.

yaml
name: Security Patch Rollout
description: Apply security patches to webserver fleet
trigger:
  type: schedule
  cron: "0 3 * * 0"
conditions:
  - type: device_count
    min: 1
    max: 50
  - type: time_window
    start: "02:00"
    end: "06:00"
actions:
  - name: Pre-check
    type: command
    target: all
    command: "df -h / && free -m"
  - name: Apply patches
    type: command
    target: all
    command: "apt update && apt upgrade -y"
    timeout: 300
  - name: Verify
    type: command
    target: all
    command: "uptime && docker ps"
  - name: Notify
    type: webhook
    url: https://hooks.slack.com/services/xxx
    payload:
      text: "Patch rollout completed for {{device_count}} devices"

Schedules

Schedules use standard cron expressions to trigger commands or workflows at specified times. You can target individual devices, groups, or all devices.

bash
renctl schedule create \
  --name "Daily Health Check" \
  --cron "0 2 * * *" \
  --command "uptime && df -h" \
  --target-group webservers

renctl schedule list
renctl schedule disable --id schedule-uuid

Conditions

Conditions gate whether a workflow executes. Multiple conditions are AND-ed together: device_count (only run if device count is within range), time_window (only run within specified hours), device_state (only if devices match state criteria), and expression (arbitrary expression evaluated server-side).

Webhooks

RenOS can both receive incoming webhooks (as triggers) and send outgoing webhooks (as actions). Incoming webhooks can trigger workflows with payload data available as variables.

bash

  --secret "whsec_xxx" \

  -H "X-Webhook-Secret: whsec_xxx" \

Bulk Operations

Execute commands across multiple devices simultaneously with built-in rate limiting and error handling:

bash
renctl exec --group webservers --command "systemctl reload nginx"
renctl exec --targets device-1,device-2 --command "df -h"
renctl exec --group all --command "uptime" \
  --timeout 30 \
  --parallel 10 \
  --ignore-errors

Cluster Operations

High Availability

RenOS supports active-passive high availability for the Core server. In a cluster configuration, one Core instance acts as the leader, handling all API requests, job scheduling, and agent communication. Standby instances remain ready to take over if the leader fails, using leader election via distributed locks in PostgreSQL.

Leader Election

Leader election uses PostgreSQL advisory locks for distributed coordination:

Core Instance 1 (Leader) |-- Holds advisory lock (key: 12345) |-- Processes API requests |-- Schedules and dispatches jobs |-- Maintains agent connections |-- Writes heartbeats to DB Core Instance 2 (Standby) |-- Attempts advisory lock (fails) |-- Polls lock every 5 seconds |-- Ready to take over |-- Minimal CPU/memory usage Core Instance 3 (Standby) |-- Same as Instance 2 |-- Ready for failover

Node Management

Cluster nodes are configured in the config.yaml or via environment variables:

yaml
cluster:
  enabled: true
  node_id: core-1
  node_name: us-east-1-core
  leader_key: renos:cluster:leader
  heartbeat_interval: 5s
  election_timeout: 15s
  standby_port: 8444

database:
  url: postgres://renos:password@postgres-host:5432/renos

redis:
  url: redis://redis-host:6379/0

nats:
  url: nats://nats-host:4222

Task Distribution

When running in cluster mode, task distribution works as follows: only the leader evaluates cron schedules and dispatches jobs; all commands go through the leader's NATS connection; file transfers use direct agent-to-agent transfers when possible, coordinated by leader; agents connect to a single Core instance; if it fails, they reconnect and are redistributed.

Scaling Note: RenOS is designed for single-server deployments in its current version. Horizontal scaling of the Core is supported for high availability but all instances share the same database, Redis, and NATS infrastructure.

Security

Authentication

JWT Authentication

All API requests (except health checks and login) require a JWT bearer token. Tokens are issued on login and expire after a configurable TTL (default: 24 hours). Token claims include user ID, email, display name, and role.

bash
TOKEN=$(curl -s -X POST http://localhost:8443/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@renos.local","password":"admin"}' | jq -r '.token')

curl -H "Authorization: Bearer $TOKEN" http://localhost:8443/api/v1/devices

OAuth2 Providers

RenOS supports OAuth2 authentication via Google, GitHub, GitLab, and Microsoft.

yaml
auth:
  oauth2:
    google:
      client_id: xxx.apps.googleusercontent.com
      client_secret: ${GOOGLE_CLIENT_SECRET}
      redirect_url: https://renos.example.com/auth/google/callback
    github:
      client_id: ${GITHUB_CLIENT_ID}
      client_secret: ${GITHUB_CLIENT_SECRET}

SSO / SAML

Enterprise SSO is supported via SAML 2.0. Configure your Identity Provider metadata:

yaml

  saml:
    idp_metadata_url: https://idp.example.com/metadata.xml

IAM Policies

Fine-grained access control can be defined using IAM policies with resource-level permissions:

json
{
  "policy": {
    "statements": [
      {
        "effect": "allow",
        "actions": ["device:read", "device:command"],
        "resources": ["device:group:webservers/*"],
        "conditions": {
          "time_before": "18:00",
          "time_after": "08:00"
        }
      }
    ]
  }
}

Encryption

At Rest

  • Secrets Vault — Encrypted with AES-256-GCM using a configurable encryption key
  • Database — Sensitive columns (tokens, secrets) encrypted at the application layer
  • Key Derivation — SHA-256 hash for key derivation from passphrase

In Transit

  • Agent Communication — mTLS with certificate verification, or WebSocket over TLS (WSS)
  • API — TLS 1.3 recommended, enforced via Nginx reverse proxy
  • Internal Services — NATS with TLS, Redis with TLS, PostgreSQL with TLS

Audit Logging

Every security-relevant action is logged with timestamp (UTC, microsecond precision), user ID and email, source IP address, action type and resource, request payload (sanitized of secrets), response status code, and duration.

bash
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8443/api/v1/audit-logs?limit=20

renctl audit export --format json --since "2026-01-01"

Secrets Vault

The Secrets Vault provides encrypted storage for sensitive data such as API keys, database passwords, and certificates. Access to the vault is controlled by RBAC policies, and all access is audit-logged.

bash
renctl vault set my-api-key --value "sk-xxx"
renctl vault get my-api-key
renctl vault list
renctl vault delete my-api-key

Go SDK

The Go SDK provides a client library for interacting with the RenOS API and building Core plugins.

go
package main

import (
    "context"
    "fmt"
    "log"
    "os"
    "github.com/renos-project/renos/sdk/go"
)

func main() {
    client := renos.NewClient(renos.Config{
        Server: "https://renos.example.com",
        Token:  os.Getenv("RENOS_TOKEN"),
    })

    devices, err := client.ListDevices(context.Background(), nil)
    if err != nil { log.Fatal(err) }
    for _, d := range devices {
        fmt.Printf("Device: %s (%s)\n", d.Name, d.Status)
    }

    result, err := client.RunCommand(context.Background(),
        "device-uuid",
        &renos.CommandRequest{Command: "uptime"},
    )
    if err != nil { log.Fatal(err) }
    fmt.Printf("Output: %s\n", result.Output)
}

Frequently Asked Questions

General

What is RenOS?

RenOS is an open-source, self-hosted platform for managing devices — desktops, servers, VMs, Docker containers, NAS devices, and mobile devices — from a single interface. It provides secure remote access, command execution, automation, monitoring, and AI-powered operations.

Is RenOS free?

Yes, RenOS is open-source and free to self-host. Commercial support plans are available for enterprise deployments.

What license does RenOS use?

RenOS is licensed under the Apache License 2.0.

Can I use RenOS behind a firewall?

Yes. Agents establish outbound connections to the Core, so no inbound ports are required on managed devices. The Core server only needs the API port (8443) open to the agent network.

Technical

What technologies is RenOS built with?

Core is written in Go, Agent in Rust, and Hub in Next.js with React and TypeScript. The platform uses PostgreSQL, Redis, and NATS for data storage and messaging.

Can I manage Windows devices?

Yes. The RenOS Agent supports Windows 10/11 and Windows Server 2019+. Some features (like Docker management) require additional configuration on Windows.

How secure is RenOS?

RenOS implements defense-in-depth security: mTLS for agent communication, JWT authentication with RBAC for API access, AES-256-GCM encryption for secrets at rest, CSRF protection, Content Security Policy headers, input validation, and comprehensive audit logging.

Does RenOS support SSO?

Yes. RenOS supports OAuth2 (Google, GitHub, GitLab, Microsoft) and SAML 2.0 for single sign-on.

Can I run multiple RenOS instances?

Yes. Multi-instance high availability is supported with active-passive failover using PostgreSQL advisory locks for leader election.

Operations

How do I backup RenOS?

Use the built-in backup script: ./scripts/backup.sh. This creates a compressed SQL dump of the database. Set up a cron job for automated daily backups.

How do I update RenOS?

Run docker compose -f docker-compose.prod.yml pull && docker compose -f docker-compose.prod.yml up -d, then run pending database migrations with renos-core migrate.

Can I use RenOS with Kubernetes?

Yes. Helm charts are available in the deploy/charts/ directory for Kubernetes deployment.

Plugins & Integration

Can I write my own plugins?

Yes. Plugins can be written in any language that compiles to WebAssembly, or as native modules in Go (Core) or Rust (Agent).

Is there a REST API?

Yes. A comprehensive REST API is available under /api/v1/ with OpenAPI documentation at /api/docs.

Does RenOS integrate with monitoring tools?

Yes. RenOS exposes Prometheus metrics and can send webhook notifications to Slack, PagerDuty, OpsGenie, and custom endpoints.
